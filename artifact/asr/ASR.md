# Architectural Significant Requirements (ASR)

_Source file: `ASR_checked_corrected_with_SRS.xlsx`_

|  |  | Function | Description | Architectural Requirements | Note |
| --- | --- | --- | --- | --- | --- |
| 1 | Authentication & Access | UC01 - Login | Authenticate users into the system.<br>Actors: Admin, District Manager, Store Manager, Cashier, Inventory Staff, Loyalty Member | Security:<br>- JWT-based authentication with secure session expiration after inactivity.<br>- Passwords must be hashed before storage and compared securely.<br>- Failed login attempts should be rate-limited and monitored.<br>- Login events must be written to audit logs.<br>Usability/Reliability:<br>- Role-based redirect after successful authentication. | Aligned with UC01; SRS 3.1 |
|  |  | UC02 - Manage Users | Create, update, deactivate, or remove user accounts.<br>Actors: Admin | Security:<br>- Strict RBAC: only Admin can create, update, deactivate, or remove users.<br>- Validate unique username/email and valid role assignment.<br>- Generate temporary password securely for new accounts.<br>- Audit all user-management operations. | Aligned with UC02; SRS 3.1 |
|  |  | UC03 - Configure Roles and Permissions | Configure RBAC roles and permissions.<br>Actors: Admin | Security:<br>- RBAC administration must be restricted to Admin.<br>- Role-permission changes must be transactional to avoid partial permission states.<br>- Audit all permission updates for traceability.<br>- Validate every permission against the permission repository. | Aligned with UC03; SRS 3.1 |
| 2 | Store Management & Dashboard | UC04 - Create or Update Store | Create or update store information.<br>Actors: Admin, District Manager | Security:<br>- Only Admin and District Manager can create or update store records.<br>- Validate duplicate store name/address and manager assignment.<br>Maintainability/Data Integrity:<br>- Store changes should be persisted through a StoreRepository/service layer.<br>- Audit store changes. | Aligned with UC04 |
|  |  | UC05 - View Store Dashboard | View store performance dashboard.<br>Actors: Admin, District Manager, Store Manager | Security:<br>- Dashboard data must be scoped by role and assigned store/region.<br>Performance:<br>- Standard dashboard must load within 3 seconds.<br>- Use Redis/cache for frequently requested KPIs where appropriate.<br>Reliability:<br>- Handle unavailable reporting/inventory/transaction data sources gracefully. | Aligned with UC05; SRS 3.2 |
| 3 | POS Operations | UC06 - Create POS Transaction | Process customer purchase at POS.<br>Actors: Cashier | Security:<br>- Cashier must have an authenticated session and active shift.<br>- Payment and transaction operations must be protected against duplicate submission.<br>Performance:<br>- POS transaction processing should complete within 2 seconds under normal load.<br>Data Integrity:<br>- Save transaction and inventory deduction atomically.<br>- Generate receipt only after successful payment. | Aligned with UC06; SRS 3.2 |
|  |  | UC07 - Apply Loyalty Member | Link loyalty member account to transaction.<br>Actors: Cashier | Security:<br>- Validate loyalty member identity/status before linking to a transaction.<br>Privacy:<br>- Minimize exposure of member data at POS.<br>Data Integrity:<br>- Recalculate eligible benefits only after successful member validation. | Aligned with UC07 |
|  |  | UC16 - Close Shift | Reconcile cashier shift.<br>Actors: Cashier, Store Manager | Security:<br>- Only shift owner or Store Manager should close/review shifts.<br>Data Integrity:<br>- Reconcile cash input against system transaction totals.<br>- Require manager review for variance above configured threshold.<br>Auditability:<br>- Store shift report and variance details. | Aligned with UC16 |
|  |  | UC17 - View Transaction History | Search and review transactions.<br>Actors: Store Manager, Cashier, Loyalty Member | Security:<br>- Restrict visible transactions based on user role and scope.<br>Performance:<br>- Use indexed search by store, cashier, member, date range, and status.<br>Usability:<br>- Paginate transaction results and support detail drill-down. | Aligned with UC17 |
| 4 | Loyalty Program | UC08 - Calculate Loyalty Points | Calculate points after transaction completion.<br>Actors: System | Data Integrity:<br>- Award points only for completed transactions linked to active loyalty members.<br>- Use active loyalty policy and tier multiplier.<br>Reliability:<br>- Log policy errors and stop safely when active policy is missing.<br>Auditability:<br>- Save point history for every earn transaction. | Aligned with UC08 |
|  |  | UC09 - Redeem Loyalty Points | Redeem points for discount.<br>Actors: Cashier, Loyalty Member | Security:<br>- Verify active member and sufficient point balance before redemption.<br>Data Integrity:<br>- Cap discount at transaction total.<br>- Deduct points and update transaction total atomically.<br>Auditability:<br>- Save redemption history. | Aligned with UC09 |
|  |  | UC10 - Upgrade Loyalty Tier | Upgrade loyalty tier automatically.<br>Actors: System | Reliability:<br>- Run tier evaluation through controlled system process/scheduler.<br>Data Integrity:<br>- Use active tier policy and completed spending history.<br>- Prevent downgrade/invalid tier transitions in upgrade flow.<br>Notification:<br>- Notify member after successful tier upgrade. | Aligned with UC10 |
| 5 | Promotion Management | UC11 - Manage Promotion | Manage promotional campaigns.<br>Actors: Admin, District Manager, Store Manager | Security:<br>- Admin, District Manager, and Store Manager permissions must be enforced.<br>Data Integrity:<br>- Validate promotion dates, discount values, target products, and conflicts.<br>Maintainability:<br>- Use scheduler to activate promotions based on start date.<br>Auditability:<br>- Audit promotion creation and updates. | Aligned with UC11 |
|  |  | UC12 - Apply Promotion to Transaction | Automatically apply eligible promotions to POS transaction.<br>Actors: System | Reliability:<br>- Promotion engine must retrieve only active promotions for current store/time.<br>Data Integrity:<br>- Apply eligibility rules consistently and select best benefit.<br>Performance:<br>- Promotion calculation should not delay POS transaction processing beyond the POS SLA. | Aligned with UC12; SRS 3.2 |
| 6 | Dynamic Pricing | UC13 - Create Pricing Rule | Create dynamic pricing rules.<br>Actors: Admin, District Manager | Security:<br>- Only Admin and District Manager can create pricing rules.<br>Data Integrity:<br>- Validate rule syntax, target products, schedules, and adjustment values.<br>Auditability:<br>- Audit pricing rule creation.<br>Maintainability:<br>- Register rule schedule through pricing scheduler. | Aligned with UC13 |
|  |  | UC14 - Execute Dynamic Pricing | Execute dynamic pricing and update prices automatically.<br>Actors: System | Performance:<br>- Dynamic pricing calculation latency should remain below 100 ms per item batch where feasible.<br>Data Integrity:<br>- Enforce minimum and maximum price boundaries.<br>Reliability:<br>- Publish price updates to POS through synchronization mechanism.<br>Auditability:<br>- Save price history and rejected-price audit entries. | Aligned with UC14; SRS 3.2 |
|  |  | UC15 - View Price History | Review historical pricing data.<br>Actors: Admin, District Manager, Store Manager | Security:<br>- Restrict price history visibility by user role.<br>Performance:<br>- Index price history by product and date range.<br>Usability:<br>- Sort results by changedAt descending and show old/new price, actor, reason, timestamp. | Aligned with UC15 |
|  |  | UC29 - A/B Test Pricing | Compare pricing strategies.<br>Actors: Admin, District Manager | Security:<br>- Only Admin and District Manager can configure pricing experiments.<br>Data Integrity:<br>- Validate variants, time window, target products, and minimum sample size.<br>Analytics:<br>- Collect comparable sales data and generate experiment result report. | Aligned with UC29 |
|  |  | UC30 - Rollback Price Change | Restore previous product price.<br>Actors: Admin | Security:<br>- Restrict rollback operation to Admin.<br>Data Integrity:<br>- Restore only a valid historical price version for the selected product.<br>Reliability:<br>- Publish rollback price update to POS.<br>Auditability:<br>- Save rollback price history and audit log. | Aligned with UC30 |
| 7 | Inventory & Transfer Management | UC18 - Manage Product Catalog | Manage products, categories, and SKU data.<br>Actors: Admin, Store Manager, Inventory Staff | Security:<br>- Admin, Store Manager, and Inventory Staff permissions must be enforced.<br>Data Integrity:<br>- Validate SKU uniqueness, category existence, barcode, and non-negative base price.<br>Auditability:<br>- Audit product catalog changes. | Aligned with UC18 |
|  |  | UC19 - Update Inventory Stock Level | Update inventory quantity.<br>Actors: Inventory Staff | Security:<br>- Inventory changes must be restricted to authorized inventory roles.<br>Data Integrity:<br>- Prevent negative stock and invalid adjustment quantities.<br>Reliability:<br>- Save inventory movements for traceability.<br>Synchronization:<br>- Inventory synchronization should be near real-time. | Aligned with UC19; SRS 3.2 |
|  |  | UC20 - Create Inter-store Transfer | Create inventory transfer request.<br>Actors: Inventory Staff | Security:<br>- Inventory Staff can create transfer requests.<br>Data Integrity:<br>- Validate source/destination stores and available stock before request creation.<br>Workflow:<br>- New transfers start as PENDING_APPROVAL and notify approver. | Aligned with UC20 |
|  |  | UC21 - Approve Transfer | Approve or reject transfer requests.<br>Actors: Store Manager, District Manager | Security:<br>- Store Manager and District Manager can approve/reject transfers.<br>Data Integrity:<br>- Process only transfers in PENDING_APPROVAL state.<br>Reliability:<br>- Move stock and update transfer status consistently.<br>Notification:<br>- Notify requester after decision. | Aligned with UC21 |
|  |  | UC25 - Set Low-stock Alert Threshold | Configure low-stock threshold.<br>Actors: Admin, Store Manager | Security:<br>- Only Admin and Store Manager can configure alert thresholds.<br>Data Integrity:<br>- Validate product, store, and non-negative threshold quantity.<br>Maintainability:<br>- Store thresholds as active alert rules. | Aligned with UC25 |
|  |  | UC26 - Receive Low-stock Notification | Receive low-stock notification.<br>Actors: Inventory Staff, System | Reliability:<br>- Monitor active inventory against configured thresholds.<br>Notification:<br>- Deliver alerts to inventory staff for the relevant store.<br>Resilience:<br>- Retry failed notifications and audit final failure. | Aligned with UC26 |
| 8 | Reporting & Analytics | UC22 - Generate Store Report | Generate store-level operational report.<br>Actors: Store Manager | Security:<br>- Store report data must be scoped to authorized store users.<br>Data Integrity:<br>- Validate report type and date range.<br>Reliability:<br>- Handle empty data and report-generation errors gracefully.<br>Persistence:<br>- Save generated report for later viewing/export. | Aligned with UC22 |
|  |  | UC23 - Generate Chain Report | Generate consolidated multi-store report.<br>Actors: Admin, District Manager | Security:<br>- Chain-level reports restricted to Admin and District Manager.<br>Performance:<br>- Aggregate multi-store data efficiently through reporting service.<br>Reliability:<br>- Warn users when synchronization is incomplete.<br>Persistence:<br>- Save consolidated report. | Aligned with UC23 |
|  |  | UC24 - View Real-time Analytics | Monitor live analytics dashboard.<br>Actors: Admin, District Manager | Security:<br>- Restrict real-time analytics to Admin and District Manager.<br>Performance/Reliability:<br>- Use WebSocket or streaming mechanism for live metric updates.<br>- Detect analytics service unavailability and show service error.<br>Scalability:<br>- Support live KPI updates without overloading reporting database. | Aligned with UC24; SRS 3.4 |
|  |  | UC28 - Export Report | Export generated reports.<br>Actors: Admin, District Manager, Store Manager | Security:<br>- User must be authorized to access the selected report before export.<br>Data Integrity:<br>- Support only approved formats: PDF, XLSX, CSV.<br>Reliability:<br>- Store exported file and generate download URL only after successful export. | Aligned with UC28 |
| 9 | Complaint Management | UC27 - Manage Complaints | Submit and handle complaints.<br>Actors: Admin, Store Manager, Loyalty Member | Security:<br>- Complaint handling restricted to Admin and Store Manager; members can submit complaints.<br>Data Integrity:<br>- Validate subject, description, resolution note, and target status.<br>Notification:<br>- Notify complaint owner after status/resolution update. | Aligned with UC27 |
| 10 | Non-Functional Architecture | Security Architecture | Covers cross-cutting security requirements from the SRS non-functional section. | Security:<br>- Support JWT authentication, RBAC, encrypted passwords, HTTPS, audit logs, rate limiting, and failed-login monitoring.<br>- Sensitive operations include price changes, inventory adjustments, transfers, and permission changes. | Aligned with SRS 3.1 |
|  |  | Performance Architecture | Covers performance targets and workload constraints defined in the SRS. | Performance:<br>- Support at least 5,000 concurrent users.<br>- POS processing <= 2 seconds under normal load.<br>- Dashboard loading <= 3 seconds for standard reports.<br>- Dynamic pricing latency < 100 ms per item batch where feasible.<br>- Inventory synchronization should be near real-time. | Aligned with SRS 3.2 |
|  |  | Availability & Reliability Architecture | Covers production reliability, backup, monitoring, and recovery requirements. | Availability/Reliability:<br>- Target 99.99% production uptime.<br>- Implement database replication, failover, automated backup, disaster recovery, monitoring, and administrator notifications. | Aligned with SRS 3.3 |
|  |  | Implementation Architecture | Covers technology stack and deployment constraints defined by the SRS. | Implementation:<br>- Frontend: ReactJS.<br>- Backend: Node.js and ExpressJS.<br>- Database: PostgreSQL.<br>- Cache: Redis.<br>- API style: RESTful.<br>- Real-time communication: WebSocket where required.<br>- Deployment: Docker. | Aligned with SRS 3.4 |
